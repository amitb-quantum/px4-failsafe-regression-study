# Erratum and review notes for the VM-venue bundle (2026-10-24)

_Written on vermithor while assembling this repository, from the VM bundle's own files and PX4
source at the pinned commits. The VM files in `reports/vm-venue/`, `harness/vm-venue/` and
`evidence/vm-venue/` are published **unmodified**; this note sits beside them. Items 1–2 are
verified. Item 3 was an observation from the code and has since been confirmed in VM logs. Item 4 is
not verified for the batch runs. Item 5 (added later the same day) reviews
`HEARTBEAT_DIAGNOSTIC.md` against PX4 source._

## 1. nav_state labels ≥ 6 are wrong in `harness/vm-venue/analyze_ulog.py` (verified)

The analyzer's `NAV_STATE` table does not match `msg/VehicleStatus.msg` at either pinned commit
(`f7ed553f`, `aa5b9ae6`; the file is identical in both). Values 0–5 are correct; every label from
6 upward is wrong:

| nav_state value | Label in VM analyzer | Correct label at the pinned commits |
|---|---|---|
| 6 | ACRO | (undefined at these commits) |
| 10 | OFFBOARD | ACRO |
| 11 | STAB | (unused) |
| 12 | AUTO_TAKEOFF | DESCEND |
| 13 | AUTO_LAND | TERMINATION |
| 14 | DESCEND | OFFBOARD |
| 15 | TERMINATION | STAB |
| 17 | ORBIT | AUTO_TAKEOFF |
| 18 | AUTO_PRECLAND | AUTO_LAND |
| 19 | AUTO_VTOL_TAKEOFF | AUTO_FOLLOW_TARGET |

The runner JSONs store labels, not numbers. Because the analyzer's mapping is one-to-one, each
label maps back to its number, and from there to the correct name.

**Effect on the VM gate: none.** The VM's scored observables are AUTO_LOITER (4), AUTO_RTL (5) and
POSCTL (2), all labelled correctly. All 24 runner entries were re-scored with corrected labels
under the approved departure rule:
- **Build B:** 10/10 valid runs pass.
- **Build A:** 10/10 valid runs are defect-positive (AUTO_RTL at +5.0 s).

The only relabel in valid runs is the end-of-run landing at ~60.1–60.6 s. It is **AUTO_LAND**
(18), not AUTO_PRECLAND, which also fits the driver's `MAV_CMD_NAV_LAND`. It falls 1.3–1.8 s after
each run's 35 s window ends, so it is not a departure.

Note: `batch_run.py`'s own `departed_rtl` field checks for the label "AUTO_LAND" anywhere after
RC loss, **with no window limit**. With correct labels, it would read `true` for every valid
Build B run, because of that post-window landing. The gate was read in the write-up with the
35 s window applied, as `BATCH_REPORT.md` states, so the verdict is unaffected. The runner field
should not be read on its own.

## 2. Stale docstring in the VM drivers (verified)

The docstrings of `smoke_run.py` and `discriminating_run.py` say the RC stream is
`RC_CHANNELS_OVERRIDE`. The code sends MAVLink `MANUAL_CONTROL` (`manual_control_send`), which
matches what `PHASE0_REPORT.md` §8 says was adopted. Documentation only.

## 3. No GCS heartbeat is sent by the VM drivers (from code; since confirmed in VM logs)

**Update:** confirmed on the VM in a valid batch Build B run. `failsafe_flags.gcs_connection_lost`
= 1 for the whole log, and `telemetry_status.heartbeat_type_gcs` = 0 on every sample (reported in
`HEARTBEAT_DIAGNOSTIC.md`). Original note follows.

The VM docstrings say telemetry stays alive "via pymavlink's heartbeat thread". The drivers never
call `heartbeat_send`, and `pymavlink.mavutil` (checked at 2.4.50) has no automatic heartbeat
sender or thread. Unless the VM's pymavlink differs, the VM harness sends **no** GCS heartbeat,
while vermithor's harness sends one at 1 Hz for the whole run.

This is a concrete link-setup difference between the venues. Whether it bears on the open Build B
difference has **not been tested**. On the VM, `telemetry_status.heartbeat_type_gcs` and
`failsafe_flags.gcs_connection_lost` in the ULogs would show it.

## 4. Manual-control stream restored ~1 s before the 35 s window ends (from smoke_B3; outcome-neutral)

The driver measures its 35 s window from when it stops the stream, while scoring measures it from
the in-log RC-loss edge, about 0.2–0.5 s later. In `PHASE0_REPORT.md` §8 (smoke_B3), the stream was
restored at 57.62 s, 1.25 s before the scoring window ended at 58.87 s. Batch runs use the same
driver timing, but their summaries do not record the lost-flag transitions, so this is not
verified for them. It does not affect any outcome: both builds' scored transitions happen at
+5.0 s.

## 5. Review of `HEARTBEAT_DIAGNOSTIC.md`: the step-1 log field cannot see the VM's link (from source; verified at the pinned commits)

`HEARTBEAT_DIAGNOSTIC.md` records the VM heartbeat test as **INCONCLUSIVE** under its own
pre-fixed rule: step 1 required `telemetry_status.heartbeat_type_gcs` to appear in the log, and it
never did. That verdict stands as recorded; this note does not re-score the run. PX4 source at the
pinned commits shows why that log field could not register this link:

- **The logger records at most 4 `telemetry_status` instances:**
  `add_optional_topic_multi("telemetry_status", 1000, 4)` (`src/modules/logger/logged_topics.cpp:140`).
- **The VM's serial link is MAVLink instance 5, the sixth instance.** Its manual-control
  `data_source=7` is `SOURCE_MAVLINK_5` (`msg/ManualControlSetpoint.msg`). This fits the startup
  script: `px4-rc.mavlink` starts GCS, offboard, payload and gimbal UDP links, plus a "sihsim" link
  for SIH. Vermithor's console shows exactly these five (ports 18570, 14580, 14280, 13030, 19450)
  before any extra link. At most four of
  the six `telemetry_status` instances can be logged. The diagnostic notes that every logged
  instance shows `rx_message_count` 0, which is consistent with the receiving link not being among
  them.
- **Commander reads all instances, not just the logged ones.** `SubscriptionMultiArray<telemetry_status_s>`
  has default size `ORB_MULTI_MAX_INSTANCES`, which is 10 in non-constrained builds such as SITL
  (`platforms/common/uORB/uORB.h`, `Commander.cpp:2514`). Instance 5 is within that limit; the
  receiver's own channel limit (`mavlink_receiver.cpp:1605`) is also 10 here.

So the step-1 field was structurally blind to the VM's link. The field that reflects commander's
own view, `failsafe_flags.gcs_connection_lost`, did change with the manipulation:
- it was 1 for the whole log in the no-heartbeat batch run;
- in the heartbeat run it cleared at 9.52 s (link-up) and stayed 0 through RC loss (23.94 s) and
  through the POSCTL return at 28.96 s;
- it set at 40.03 s and cleared again at 60.50 s, for reasons that remain unexplained.

**Reading (reviewer's, not the VM's verdict):** a GCS heartbeat appears to have been registered by
commander at the moment Build B left Hold, and Build B still returned to POSCTL at +5.01 s. That
leans toward the GCS heartbeat **not** explaining the venue difference (the REFUTED pattern). It is
not adopted as a verdict, for three reasons:
- the test's pre-fixed step-1 rule named a different gauge;
- the 40.03 s toggle is unexplained;
- the serial instance's own `telemetry_status` was not logged, so registration is inferred from
  `gcs_connection_lost` rather than observed directly.

A rerun that checks registration via `gcs_connection_lost`, or via a logger setting that records
more `telemetry_status` instances, would settle it.
